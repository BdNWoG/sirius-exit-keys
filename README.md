# Sirius exit-claim proving key (`ExitClaim`, v1)

This repository publishes the **Groth16 proving key for the Sirius `ExitClaim`
circuit** so that any user can generate their own exit proof and withdraw from
the Sirius rollup **without the operator's cooperation, servers, or data**.

A proving key is **not a secret**. The "toxic waste" of a Groth16 trusted setup
is the discarded setup randomness, not the proving key. Withholding a proving
key is a distribution choice, never a cryptographic necessity — and withholding
this one made a self-custody claim untrue. Hence this repo.


## Verify this is the key the deployed program actually accepts

Do not trust the table above, or filenames, or dates. Check it against the
chain. The Solana devnet program `2sz5LgzjAQC9BFz4xPPAR3WbHCsQqU2PECWjmpb18d1H`
stores its `ExitClaim` verifying key in the PDA
`FoneiBweDYm6W9zgnbCcrETemsCo8rmpcHc46atL4S51`
(seeds `["verifier", 0x02]`). Reconstruct the 832-byte VK from that account and
compare:

```bash
# VerifierState layout: 8 discriminator | 1 proof_type | 1 nr_pubinputs
#   | 64 alpha_g1 | 128 beta_g2 | 128 gamma_g2 | 128 delta_g2
#   | 768 vk_ic | 1 bump | 32 canonical_vk_hash
#
# The on-chain 832-byte VK is bytes [10..458] (alpha|beta|gamma|delta)
# followed by the first (nr_pubinputs + 1) * 64 = 384 bytes of vk_ic.

solana account FoneiBweDYm6W9zgnbCcrETemsCo8rmpcHc46atL4S51 \
  --url https://api.devnet.solana.com --output-file onchain.bin

python3 - <<'PY'
import hashlib
d = open('onchain.bin','rb').read()
nr = d[9]
vk = d[10:458] + d[458:458 + (nr+1)*64]
print('nr_pubinputs      ', nr)
print('on-chain VK sha256', hashlib.sha256(vk).hexdigest())
print('stored vk hash    ', d[1227:1259].hex())
PY
```

Expected:

```
nr_pubinputs       5
on-chain VK sha256 ad13f9e3a80fb6b2ea133f8dede65b86352669a3a6c024fcbd3ad8133f82fc32
stored vk hash     66838a20ef9efb66522132bf25b01792d9aa241ed200f2ae84a03b224eb16c94
```

`on-chain VK sha256` must equal the `vk_exit_claim.solana.bin` hash in the table.
If it does not, **this bundle is stale and proofs made with it will be rejected**
— open an issue rather than using it.

## Verify the proving key really pairs with that verifying key

The strongest check, and the only one that rules out a mismatched setup: make a
real proof with `exit_claim_pk.bin` and verify it under `exit_claim_vk.bin`.
In the `sirius-main` repo:

```bash
go test ./circuit -run TestExitClaim_KeyPairBinding -v \
  -args -exit-claim-keys=/path/to/this/repo \
        -exit-claim-solana-vk-sha256=ad13f9e3a80fb6b2ea133f8dede65b86352669a3a6c024fcbd3ad8133f82fc32
```

(Rename the files to `pk.bin` / `vk.bin` / `r1cs.bin`, the names that test expects.)

## Why this matters / non-reproducibility

gnark's `groth16.Setup` is **unseeded**. The `ExitClaim` circuit is fully
deterministic (9,337 constraints), but running the setup yourself produces a
*different* proving/verifying key pair, and the deployed on-chain verifier only
accepts proofs under the specific verifying key above. So this exact file cannot
be regenerated by anyone — it can only be preserved and distributed. That is why
it is here, and why it is mirrored (see below).

At least one other `ExitClaim` key bundle exists that is **not** the deployed one
(a later re-bake). Its Solana VK hashes to `334323d6…`, and proofs made with it
are rejected on-chain. Always run the on-chain check above.

## Circuit

`ExitClaimCircuit`, BN254, 9,337 constraints, 5 public inputs:
`exit_root`, `account_id`, `shares_withdrawable`, `exit_nonce`, `destination`.
Private witness: a depth-32 Merkle path (`Siblings[32]`, `PathBits[32]`).

Proving is cheap: the key loads in ~70 ms and a proof takes ~30 ms on one CPU
core. No GPU, no large machine.
